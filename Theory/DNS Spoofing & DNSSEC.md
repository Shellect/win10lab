# Часть 1. DNS Spoofing

## 1.1. Зачем вообще атакуют DNS

Пользователь почти никогда не вводит IP. Он пишет имя: `www.lab.local`, `bank.example`. Приложение спрашивает DNS: «какой IPv4 у этого имени?» — и дальше соединяется уже с полученным адресом.

Если подменить ответ DNS, жертва сама «добровольно» пойдёт на чужой хост:

* откроет фишинговый сайт вместо банка;
* отправит пароль на сервер злоумышленника;
* скачает «обновление» с поддельного зеркала.

Атакующий не обязан взламывать сам веб-сервер: достаточно солгать на этапе **разрешения имени**.

Классический DNS **не проверяет подлинность** ответа криптографически: клиент доверяет тому, что пришло «как будто от DNS-сервера», если совпали технические поля пакета (порт, ID запроса и т.д.). Этим и пользуются при spoofing.

## 1.2. Как выглядит нормальный DNS-обмен

Упрощённо (клиент PC1, сервер в red.net):

1. Приложение на PC1 вызывает резолвер ОС.
2. ОС смотрит `/etc/hosts`, кэш; если нет — шлёт **DNS Query** (обычно **UDP, порт 53**) на адрес из `resolv.conf` (у нас `172.16.20.53`).
3. В запросе: имя (`www.lab.local`), тип записи (часто **A** — имя → IPv4).
4. BIND на Alpine ищет зону, формирует **DNS Response** с A-записью `172.16.20.53`.
5. Клиент принимает первый подходящий ответ и кэширует его на время **TTL**.

Важные поля пакета (их видно в Wireshark):

| Поле | Зачем |
| :--- | :--- |
| Transaction ID (16 бит) | Связывает ответ с запросом |
| Question | Какое имя и тип спрашивали |
| Answer | Записи ответа (A, NS, …) |
| Flags | QR (запрос/ответ), AA (авторитетный) и др. |

Если злоумышленник успеет подсунуть ответ с тем же ID и «правильным» вопросом, клиент может принять его за настоящий.

## 1.3. Что такое DNS Spoofing

**DNS Spoofing** — подмена DNS-ответа так, чтобы имя указывало на IP, выбранный атакующим, а не на адрес из настоящей зоны.

Родственные понятия:

| Термин | Смысл |
| :--- | :--- |
| **DNS Spoofing** | Общее: поддельный ответ DNS |
| **DNS Cache Poisoning** | Подмена / отравление кэша резолвера (ложь «запоминается» и раздаётся многим) |
| **DNS Hijacking** | Перехват резолвинга шире: смена DNS у роутера, вредонос на ПК, атака на регистратора |
| **MITM + dns_spoof** | Человек посередине видит запрос и сам отвечает (как в нашей лабораторной с Ettercap) |

В третьей лабораторной — именно **локальный spoofing через MITM** (ARP poisoning + плагин `dns_spoof`), а не классическое удалённое отравление кэша «вслепую» по Kaminsky.

## 1.4. Два основных сценария атаки

### A. On-path / MITM (наша лаборатория)

Атакующий **видит** DNS-запрос жертвы (стоит на пути или зеркалирует трафик) и отвечает быстрее настоящего сервера или вместо него.

Типичная цепочка в LAN:

1. **ARP Spoofing (ARP poisoning):** Attacker убеждает жертву, что MAC шлюза — это MAC Attacker; шлюз — что MAC жертвы — тоже он. Весь трафик жертвы↔шлюз идёт через Attacker.
2. Жертва шлёт DNS Query к `172.16.20.53`. Пакет попадает к Attacker.
3. Плагин **dns_spoof** смотрит имя в запросе, сверяет с `/etc/ettercap/etter.dns` и шлёт **поддельный Response**: `www.lab.local → 172.16.10.10`.
4. Жертва принимает ответ. Настоящий ответ от Alpine может прийти позже — часто уже поздно (первый подходящий выиграл).

Почему Attacker должен быть в **blue.net** (тот же Switch1):

* ARP — протокол **канального уровня**, работает в пределах одного широковещательного домена.
* Из red.net или «из Интернета» отравить ARP таблицы в blue.net напрямую нельзя.
* Firewall на MikroTik (разрешить UDP/53 blue→DNS) **не мешает** атаке: подмена происходит *до* того, как запрос честно дойдёт до red.net, либо параллельно с ним на L2.

```text
  PC1                    Attacker                 MikroTik              Alpine DNS
   |                        |                        |                      |
   |--- ARP: кто .254? ---->|                        |                      |
   |<-- ARP: я (.10) -------|                        |                      |
   |                        |                        |                      |
   |--- DNS Query www ------|--- (может уйти дальше) ----------------------->|
   |<-- DNS Reply: .10 -----|                        |                      |
   |                        |                        |   (настоящий Reply)  |
   |<-----------------------|------------------------|<--- A 172.16.20.53 --|
```

Побеждает тот ответ, который клиент принял первым / которому доверился.

### B. Off-path cache poisoning (кратко, для кругозора)

Атакующий **не** на пути. Он пытается угадать Transaction ID (и раньше — ещё и исходный порт) и засыпать резолвер поддельными ответами, пока жертва (или сам резолвер) ждёт настоящий.

Исторически (атака Kaminsky, 2008) это было особенно опасно для кэширующих резолверов. Современные резолверы используют:

* случайный Transaction ID;
* случайный исходный UDP-порт;
* проверки согласованности ответа с запросом;
* часто DNSSEC / DNS over HTTPS/TLS вверху стека.

В нашей GNS3-лаборатории мы этот сценарий не воспроизводим — он сложнее и менее нагляден, чем MITM + Ettercap.

## 1.5. Что делает Ettercap в шагах лабораторной

| Действие | Смысл |
| :--- | :--- |
| Unified sniffing | Слушать и вмешиваться в трафик на выбранном интерфейсе |
| Scan for hosts | ARP-скан: кто жив в подсети |
| Target 1 = жертва, Target 2 = шлюз | Пара для MITM |
| ARP poisoning | Подмена ARP-записей → трафик через Attacker |
| Плагин `dns_spoof` | На DNS Query к именам из `etter.dns` отвечать своим A |
| Строка `www.lab.local A 172.16.10.10` | Конкретная ложь: имя → IP Attacker |

Файл `etter.conf` (`ec_uid`/`ec_gid` = 0, iptables) нужен, чтобы процесс мог перехватывать и перенаправлять пакеты от имени root.

Веб-сервер на Attacker (Apache / darkhttpd) — не обязателен для spoofing, но нагляден: жертва открывает `http://www.lab.local` и видит страницу злоумышленника.

## 1.6. Последствия успешной атаки

* Фишинг и кража учётных данных.
* Подмена обновлений / репозиториев.
* Перехват почты и API, если клиент ходит по имени без дополнительной проверки сертификата (или игнорирует ошибки TLS).
* Закрепление через кэш: пока жив TTL поддельной записи, повторные запросы могут не ходить к настоящему DNS.

Важно: **HTTPS** снижает ущерб, если клиент проверяет сертификат: у атакующего нет валидного сертификата на `www.lab.local` от доверенного CA. Но пользователь может кликнуть «всё равно продолжить»; бывают и атаки на сами CA / ошибки конфигурации. DNS spoofing всё равно опасен для незашифрованных сервисов и для первого шага атаки.

## 1.7. Как заметить атаку в лаборатории

В Wireshark на линке PC1↔Switch1:

* много **ARP** reply «я — `172.16.10.254`» с MAC Attacker;
* два разных **DNS Response** на один Query (поддельный и настоящий) или подозрительно быстрый ответ с «чужого» MAC;
* в ответе A-запись `172.16.10.10` вместо `172.16.20.53`.

На клиенте: сравнить `nslookup` **до** и **после** включения плагина.

## 1.8. Защита без DNSSEC (и рядом с ним)

| Мера | Что даёт | Ограничение |
| :--- | :--- | :--- |
| Запись в `/etc/hosts` | Имя не резолвится через DNS | Только для известных имён; не масштабируется |
| DNS только по TLS/HTTPS (DoT/DoH) | Сложнее подменить ответ на пути | Не спасает, если скомпрометирован сам резолвер; в Tiny Core обычно нет |
| Фильтрация DNS на MikroTik | Контроль, *куда* можно ходить за DNS | Не защищает от MITM в blue.net |
| DAI / Port Security / статический ARP | Мешают ARP poisoning | Нужны управляемые коммутаторы |
| Проверка TLS-сертификатов | Не пускает на «чужой» сайт по HTTPS | Не чинит сам DNS; пользователь может обойти предупреждение |
| **DNSSEC** | Криптографическая проверка данных зоны | См. часть 2 |

В лабораторном шаге 7 `/etc/hosts` — учебный «щит»: показать, что приложение может обойти отравленный DNS для конкретного имени.

# Часть 2. DNSSEC

## 2.1. Какую проблему решает DNSSEC

**DNSSEC (Domain Name System Security Extensions)** добавляет к DNS **аутентификацию происхождения данных** и **защиту целостности**.

Простыми словами:

* ответ действительно относится к той зоне, за которую отвечает заявленный ключ;
* записи по пути **не изменили** (не подменили A-запись на IP атакующего).

DNSSEC **не** делает DNS конфиденциальным: запросы и ответы по-прежнему можно читать (это не шифрование канала). Для шифрования канала используют DoT/DoH; DNSSEC — про «можно ли верить содержимому».

| Свойство | Обычный DNS | DNSSEC |
| :--- | :--- | :--- |
| Целостность записей | Нет | Да (подписи) |
| Подлинность (от «правильной» зоны) | Нет | Да (цепочка доверия) |
| Шифрование запроса/ответа | Нет | Нет (само по себе) |
| Защита от MITM-подмены A | Нет | Да, если валидатор включён и цепочка полная |

Если в нашей атаке клиент (или резолвер) **валидирует DNSSEC**, а зона подписана, поддельный ответ Ettercap **без валидной подписи** будет отвергнут (SERVFAIL / отсутствие данных), а не принят как `172.16.10.10`.

## 2.2. Идея электронной подписи (на пальцах)

1. У зоны есть **пара ключей**: закрытый (только на сервере) и открытый (публикуется в DNS).
2. Сервер считает хэш набора записей (например, всех A для `www`) и **подписывает** хэш закрытым ключом → получается запись **RRSIG**.
3. Валидатор берёт открытый ключ, проверяет подпись. Совпало — данные не трогали. Не совпало или подписи нет при ожидании DNSSEC — ответ не принимают.

Подделать подпись без закрытого ключа вычислительно нереально (при нормальной криптографии). Attacker с Ettercap может соврать A-запись, но **не сможет** создать корректный RRSIG от ключа настоящей зоны.

## 2.3. Ключевые типы записей DNSSEC

| Тип | Назначение |
| :--- | :--- |
| **DNSKEY** | Открытые ключи зоны |
| **RRSIG** | Подпись набора записей (RRSet) данного имени и типа |
| **DS** | «Отпечаток» ключа дочерней зоны; хранится у *родителя* (связка в цепочке доверия) |
| **NSEC / NSEC3** | Доказательство, что имени *нет* (защита от подделки «имя не существует») |

Дополнительно на практике важны:

* **ZSK (Zone Signing Key)** — ключом подписывают записи зоны (RRSIG для A, NS, …). Меняют чаще.
* **KSK (Key Signing Key)** — подписывает набор DNSKEY; его отпечаток обычно уходит родителю как **DS**. Меняют реже, процедура ответственнее.

В BIND при генерации ключей флаг `-f KSK` как раз для ключа подписи ключей.

## 2.4. Цепочка доверия (Chain of Trust)

Валидатору нужен **якорь доверия (trust anchor)** — обычно ключ корня DNS (`.`), встроенный в ПО резолвера.

Цепочка вниз:

```text
.  (корень, trust anchor)
 └─ DS → DNSKEY зоны .org (пример)
      └─ DS → DNSKEY example.org
           └─ RRSIG над A www.example.org
```

Для учебной зоны `lab.local` в GNS3 «настоящего» родителя в Интернете нет: это **локальная** зона. Полноценную цепочку до корня для `lab.local` в лаборатории обычно **не строят**. Поэтому:

* в теории DNSSEC защищает от spoofing;
* на практике в нашем стенде проще показать идею и/или `/etc/hosts`, чем поднять полную валидацию с DS у родителя.

Чтобы DNSSEC «работал» в лаборатории end-to-end, нужно: подписать зону на Alpine, научить резолвер доверять вашему KSK (свой trust anchor) и включить валидацию. Это отдельный продвинутый практикум.

## 2.5. Как валидатор проверяет ответ

Упрощённый алгоритм:

1. Получен ответ с A и (желательно) RRSIG.
2. Достать DNSKEY зоны (или взять из кэша).
3. Проверить RRSIG открытым ключом.
4. Убедиться, что этому DNSKEY можно доверять: есть DS у родителя, и тот DS тоже в цепочке до trust anchor.
5. Если на любом шаге провал — ответ **невалиден** (для строгого валидатора это ошибка, а не «поверю и так»).

Без включённой валидации на клиенте/резолвере наличие подписей на сервере **само по себе** клиента не защитит: Ettercap по-прежнему может скормить голый A без RRSIG, и старый клиент его съест.

## 2.6. Что DNSSEC не обещает

* Не шифрует трафик DNS (содержимое видно на пути).
* Не заменяет HTTPS / сертификаты сайтов.
* Не защищает, если закрытый ключ зоны украден.
* Не помогает, если пользователь ходит на IP напрямую, минуя DNS.
* Сложность эксплуатации: протухшие подписи (срок в RRSIG), ошибки при ротации ключей — зона может «отвалиться» для валидирующих резолверов по всему миру.

## 2.7. DNSSEC на стороне BIND (обзор шагов)

Имеет смысл как ориентир (детали зависят от версии BIND/Alpine):

1. Установить инструменты (`bind`, утилиты `dnssec-*`).
2. Сгенерировать ZSK и KSK (`dnssec-keygen`).
3. Подключить ключи к зоне (`key-directory`, `inline-signing` / `dnssec-policy` в современных BIND).
4. Подписать зону / включить автоподписание (`rndc` / `auto-dnssec` — синтаксис зависит от версии).
5. Проверить: `dig +dnssec www.lab.local @172.16.20.53` — в ответе должны быть **RRSIG** (и при полном запросе — DNSKEY).
6. На валидирующем резолвере добавить trust anchor для `lab.local` (лабораторный костыль) либо встроить зону в тестовую иерархию с DS.

В третьей лабораторной **обязательная** полная настройка DNSSEC не требуется: достаточно понимать, *почему* подпись останавливает spoofing, и уметь объяснить отличие от `/etc/hosts`.

**Практика подписи зоны на Alpine** — в [Четвёртой лабораторной](../Lab/Четвёртая%20лабораторная%20работа.md) и [конспекте к четвёртой](../Notes/Теоретический%20конспект%20к%20четвёртой%20лабораторной.md). Отдельный валидирующий резолвер и повтор Ettercap в обязательную часть Lab 4 не входят: без валидации клиент по-прежнему может принять поддельный ответ.

## 2.8. Сравнение мер в контексте нашей топологии

| Вопрос | DNS Spoofing (Ettercap) | Защита `/etc/hosts` | DNSSEC (при валидации) |
| :--- | :--- | :--- | :--- |
| Где действует | blue.net, L2 MITM | Только на этой машине | На валидирующем резолвере |
| Что ломает атаку | — | Обход DNS для имени | Проверка подписи RRSet |
| Масштаб | Одна атака — много жертв в LAN | По одному имени на хост | Вся зона / интернет при цепочке |
| Защищает ли MikroTik FW | Нет | Не при чём | Не при чём (это L7/крипто) |

# Часть 3. Связь с третьей лабораторной

| Шаг практики | Что иллюстрирует из теории |
| :--- | :--- |
| Проверка `nslookup` до атаки | Нормальный DNS: A = `172.16.20.53` |
| Attacker в blue.net | Нужен общий L2 для ARP |
| ARP poisoning + Target жертва/шлюз | MITM on-path |
| `etter.dns` → `www.lab.local A 172.16.10.10` | Содержание лжи |
| Плагин `dns_spoof` | Поддельный Response |
| Wireshark ARP/DNS | Наблюдение spoofing |
| `/etc/hosts` | Локальный обход отравленного DNS |
| Обсуждение DNSSEC | Криптографическая целостность зоны |
| Подпись зоны (Lab 4) | На сервере появляются RRSIG/DNSKEY; защита клиента — только при валидации |

**Итог:** DNS Spoofing обманывает клиента на этапе «имя → IP». В LAN это часто делают через ARP MITM. DNSSEC отвечает на угрозу подписими и цепочкой доверия: поддельный ответ без ключа зоны не проходит валидацию. Firewall между blue и red полезен для политики DMZ, но сам по себе от spoofing внутри blue.net не спасает.
