# Настройка DMZ в Alpine

Пошаговая настройка DNS-сервера (BIND9) на Alpine Linux в сегменте **red.net** (DMZ) для [Второй лабораторной работы](../Lab/Вторая%20лабораторная%20работа.md).

| Параметр | Значение |
| :--- | :--- |
| Сегмент | **red.net** (DMZ / серверная) |
| ОС | Alpine Linux (VirtualBox) |
| IP DNS | `172.16.20.53/24` |
| Шлюз (MikroTik `ether2`) | `172.16.20.254` |
| Зона | `lab.local` |
| Клиенты | **blue.net** — `172.16.10.0/24` |

### Шаг 1: Виртуальная машина

1. Скачайте минимальный ISO Alpine (Standard или Virtual, ~50–150 МБ).
2. Создайте VM в VirtualBox: 1 vCPU, 256–512 МБ RAM, диск 1–2 ГБ.
3. Установите систему (`setup-alpine`).
4. Добавьте VM в GNS3: `Edit` → `Preferences` → `VirtualBox VMs` → `New`.
5. Подключите узел к коммутатору **red.net** (DMZ) в топологии лабораторной.

### Шаг 2: Проверка IP

Проверьте, IP адрес. Mikrotik должен выдать адрес `172.16.20.53`

```bash
ip addr show eth0
```

### Шаг 3: Установка BIND

```bash
apk update
apk add bind bind-tools
```

### Шаг 4: Конфигурация зон

Создайте файл основной конфигурации `/etc/bind/named.conf`
```bash
cp /etc/bind/named.conf.authoritative named.conf
```
Отредактируйте `/etc/bind/named.conf`:

Содержимое:

```text
options {
    directory "/var/bind";

    // Слушаем на всех интерфейсах (важно для GNS3)
    listen-on { any; };
    listen-on-v6 { none; };

    // Разрешаем запросы от клиентов blue.net и localhost
    allow-query { localhost; 172.16.10.0/24; 172.16.20.0/24; };
    
    // Разрешаем рекурсию (для кэширования внешних запросов)
    recursion yes;

    // Отключаем DNSSEC-валидацию для простоты в лабораторной среде
    dnssec-validation no;

    // Форвардеры (если нужно разрешать внешние имена через шлюз MikroTik)
    // Если MikroTik не настроен как DNS, укажите публичные (например, 8.8.8.8)
    forwarders {
        172.16.20.254;
    };
};

// Подключаем локальные зоны
include "/etc/bind/named.conf.zones";
```
Здесь мы объявляем зону прямого просмотра (lab.local) и обратную зону (20.16.172.in-addr.arpa)

Отредактируйте файл с настройками зон `/etc/bind/named.conf.zones`:

Содержимое:

```text
zone "lab.local" {
    type master;
    file "/etc/bind/db.lab.local";
};

zone "20.16.172.in-addr.arpa" {
    type master;
    file "/etc/bind/db.172.16.20";
};
```

### Шаг 5: Файлы зон

##### Общая структура db-файла

Файл зоны состоит из трёх частей:

- Директивы ($TTL, $ORIGIN) — управляют поведением парсера.
- SOA-запись — «паспорт» зоны, обязательна и всегда идёт первой.
- Ресурсные записи (RR) — NS, A, PTR, CNAME, MX и т.д.

##### Директивы

`$TTL 3600` Time To Live по умолчанию для всех записей в файле (в секундах). Если у конкретной записи не указан свой TTL, используется этот. 3600 = 1 час — сколько секунд клиенты и кэширующие резолверы могут держать запись в кэше, прежде чем перезапросить её.

`$ORIGIN lab.local.` (в примерах ниже не указан, но может присутствовать) Задаёт «базовое» имя, которое дописывается ко всем именам без завершающей точки. Если $ORIGIN lab.local., то www превращается в www.lab.local.. Обычно BIND берёт ORIGIN из имени зоны в named.conf, поэтому явно указывать не обязательно.

**SOA-запись (Start Of Authority)**
`@` — сокращение для «текущей зоны», то есть lab.local.. Именно поэтому SOA обычно записывается с @.

`IN` — класс записи (Internet). Практически всегда IN, другие классы (CH, HS) сегодня не используются.

`SOA` — тип записи. Их в зоне ровно одна.

`ns1.lab.local.` — Primary Master (MNAME). Имя главного DNS-сервера, который является источником истины для этой зоны. Именно сюда вторичные серверы обращаются за обновлениями. Точка в конце обязательна — иначе BIND допишет lab.local. и получится ns1.lab.local.lab.local..

`admin.lab.local.` — RNAME, контакт администратора. Записывается с точкой вместо @, потому что @ в BIND — это специальный символ. То есть admin.lab.local. читается как admin@lab.local.

Скобки `( ... )` — позволяют переносить запись на несколько строк. Внутри — пять чисел:

| Параметр | Значение в примере | Что означает |
| :--- | :--- | :--- |
| Serial | 2026092101 | Версия зоны. | Формат обычно YYYYMMDDNN.Увеличивается при каждом изменении — вторичные серверы сравнивают Serial и решают, обновляться ли.|
| Refresh | 3600 | Как часто (в секундах) вторичный сервер опрашивает primary на предмет изменений.|
| Retry | 900 | Через сколько секунд повторить попытку, если Refresh не удался.|
| Expire | 604800 | Через сколько секунд вторичный сервер перестанет отвечать, если так и не связался с primary. 604800 = 7 дней.|
| Negative Cache TTL | 300 | Сколько секунд кэшировать ответ «записи не существует» (NXDOMAIN).|

В обратной зоне SOA выглядит так же, только @ указывает на 20.16.172.in-addr.arpa.

##### Ресурсные записи
`@ IN NS ns1.lab.local.` NS-запись (Name Server) — объявляет, какие серверы авторитативны для зоны. Должна быть как минимум одна, и имя в ней должно совпадать с MNAME в SOA. Обычно для надёжности указывают две NS-записи (primary и secondary), но в лабе достаточно одной.

`ns1 IN A 172.16.20.53` A-запись (Address) — сопоставляет имя IPv4-адресу. Здесь ns1 без точки, поэтому BIND дополнит его до ns1.lab.local.

`www IN A 172.16.20.53` Обычная A-запись для веб-сервера. В лабе можно указать тот же IP, что у DNS — это нормально.

`53 IN PTR ns1.lab.local.` PTR-запись (Pointer) — обратное сопоставление: IP → имя. Используется только в обратных зонах. Указывается только последний октет (53), потому что остальное (172.16.20) уже задано именем зоны 20.16.172.in-addr.arpa.

##### Формат строки RR

Любая ресурсная запись состоит из полей:

```text
[имя]  [TTL]  [класс]  [тип]  [данные]
```

- имя — если не указано, берётся имя из предыдущей записи (удобно для нескольких PTR подряд).
- TTL — необязательно; если нет, используется $TTL.
- класс — IN (можно опускать, BIND подставит).
- тип — A, NS, PTR, CNAME, MX, TXT и т.д.
- данные — зависят от типа.

##### Приступаем к созданию конфигурации:

Файл зоны прямого просмотра: `/etc/bind/zones/db.lab.local`

```bash
nano /etc/bind/db.lab.local
```

или 
```bash
vi /etc/bind/db.lab.local
```

Содержимое:

```text
$TTL    604800
@       IN      SOA     ns1.lab.local. admin.lab.local. (
                          2         ; Serial
                     604800         ; Refresh
                      86400         ; Retry
                    2419200         ; Expire
                     604800 )       ; Negative Cache TTL
;
@       IN      NS      ns1.lab.local.
ns1     IN      A       172.16.20.53
www     IN      A       172.16.20.53
```

Пояснение:

    @ — это сама зона lab.local.

    admin.lab.local. — email администратора (точка вместо @).

    Serial — критически важный параметр. После любых изменений в файле увеличивайте это число (например, на +1), иначе BIND не перечитает зону

Файл зоны обратного просмотра: `/etc/bind/zones/db.172.16.20`

```bash
nano /etc/bind/db.172.16.20
```

или

```bash
vi /etc/bind/db.172.16.20
```

```text
$TTL    604800
@       IN      SOA     ns1.lab.local. admin.lab.local. (
                          2         ; Serial
                     604800         ; Refresh
                      86400         ; Retry
                    2419200         ; Expire
                     604800 )       ; Negative Cache TTL
;
@       IN      NS      ns1.lab.local.
53      IN      PTR     ns1.lab.local.
```
Пояснение: Для сети /24 в обратной зоне указывается только последний октет IP-адреса (в вашем случае 53), а полный IP собирается из имени зоны (20.16.172) и этого октета

Права:

```bash
chown named:named /etc/bind/db.lab.local /etc/bind/db.172.16.20
chmod 644 /etc/bind/db.lab.local /etc/bind/db.172.16.20
```

### Шаг 6: Проверка и запуск (OpenRC)

```bash
# 1. Проверка основного конфига
named-checkconf
# 2. Проверка зоны прямого просмотра
named-checkzone lab.local /etc/bind/db.lab.local
# 3. Проверка зоны обратного просмотра
named-checkzone 20.16.172.in-addr.arpa /etc/bind/db.172.16.20
# Если все три команды вернули OK, перезапускаем службу:
rc-service named restart
rc-service named status
rc-update add named default
```

### Шаг 7. Тестирование

На самом DNS сервере (172.16.20.53):

```bash
# Прямой запрос
dig ns1.lab.local @127.0.0.1
dig www.lab.local @127.0.0.1
# Обратный запрос
dig -x 172.16.20.53 @127.0.0.1
```

С другой машины (например, из blue.net):

```bash
dig ns1.lab.local @172.16.20.53
```

##### Предупреждения в dig — что они значат

Это не ошибки, а предупреждения, которые BIND всегда выдаёт в такой ситуации:

1. WARNING: .local is reserved for Multicast DNS
Домен .local зарезервирован под mDNS (RFC 6762, используется Avahi/Bonjour). BIND предупреждает, что использование .local для обычного DNS может конфликтовать с mDNS. Для лабораторной работы это некритично, но в реальной сети лучше использовать .lab или .internal. У вас по заданию lab.local — оставляйте как есть, просто знайте про это.

2. WARNING: recursion requested but not available
dig по умолчанию просит рекурсию (RD-флаг), а BIND её не выполняет для зоны lab.local, потому что он авторитативен для неё. Это нормальное поведение: авторитативный сервер отвечает из своей зоны, а не ищет ответ где-то ещё. Для запросов к своему же серверу это ожидаемо.

### Замечания

* IP `172.16.20.53` должен совпадать с адресом Alpine в DMZ.
* После правок зоны увеличивайте **Serial**.
* Логи: `sudo tail -f /var/log/messages | grep named`.
* Если named не отвечает снаружи — проверьте `listen-on { any; };`.
