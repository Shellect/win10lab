# Четвёртая лабораторная работа

Эта работа продолжает [Первую](Первая%20лабораторная%20работа.md), [Вторую](Вторая%20лабораторная%20работа.md) и [Третью](Третья%20лабораторная%20работа.md): тот же MikroTik, **blue.net** / **red.net**, DNS на Alpine. Цель — на практике **подписать зону** и увидеть записи DNSSEC.

**Теория:** [Теоретический конспект к четвёртой лабораторной](../Notes/Теоретический%20конспект%20к%20четвёртой%20лабораторной.md). Подробно: [DNS Spoofing и DNSSEC](../Theory/DNS%20Spoofing%20и%20DNSSEC.md) — часть 2.

**Предусловие:** вторая лабораторная выполнена — `dig www.lab.local @172.16.20.53` возвращает `172.16.20.53`. Топологию не меняем: работаем только на Alpine в **red.net**.

> Синтаксис BIND зависит от версии. Если команда или директива не принимаются — сверьте `named -v` с документацией вашей сборки Alpine и при необходимости используйте `dnssec-policy` вместо устаревшего `auto-dnssec`.

### Общий план

| Что | Детали |
| :--- | :--- |
| Где | Alpine DNS `172.16.20.53`, зона `lab.local` |
| Что делаем | Генерируем KSK/ZSK, включаем подписание, проверяем `dig +dnssec` |
| Чего нет в обязательной части | Отдельный валидирующий резолвер и повтор Ettercap (см. вывод в шаге 6) |

### Шаг 1: Контроль «до DNSSEC»

На Alpine или с клиента:

```bash
dig www.lab.local @172.16.20.53
```

В ответе должна быть A-запись `172.16.20.53`. Запишите вывод — пригодится для сравнения.

### Шаг 2: Каталог ключей и генерация KSK / ZSK

На Alpine:

```bash
sudo mkdir -p /etc/bind/keys
sudo chown named:named /etc/bind/keys
cd /etc/bind/keys

# ZSK — ключ подписи записей зоны
sudo dnssec-keygen -a RSASHA256 -b 2048 -n ZONE lab.local

# KSK — ключ подписи ключей (флаг KSK)
sudo dnssec-keygen -a RSASHA256 -b 2048 -n ZONE -f KSK lab.local

sudo chown named:named /etc/bind/keys/Klab.local.+*
ls -la /etc/bind/keys/
```

Появятся пары файлов `.key` / `.private` для ZSK и KSK.

### Шаг 3: Включить подписание в конфигурации зоны

Откройте `/etc/bind/named.conf.zones` (или тот файл, где объявлена зона `lab.local`). Для зоны прямого просмотра приведите блок к виду (классический вариант BIND 9):

```text
zone "lab.local" {
    type master;
    file "/etc/bind/db.lab.local";
    key-directory "/etc/bind/keys";
    inline-signing yes;
    auto-dnssec maintain;
};
```

Обратную зону в этой лабораторной можно не подписывать — достаточно прямой `lab.local`.

Проверка конфигурации:

```bash
sudo named-checkconf
```

Если `auto-dnssec` / `inline-signing` отвергнуты вашей версией BIND — перейдите на `dnssec-policy` по документации BIND для вашей версии (смысл тот же: зона должна подписываться автоматически).

### Шаг 4: Перезапуск named и загрузка ключей

```bash
sudo rc-service named restart
sudo rc-service named status
```

При наличии `rndc`:

```bash
sudo rndc loadkeys lab.local
sudo rndc sign lab.local
```

(Если `rndc` не настроен, после `inline-signing` / `auto-dnssec maintain` часто достаточно перезапуска `named` — подождите несколько секунд.)

Логи при ошибках: `sudo tail -50 /var/log/messages | grep named`.

### Шаг 5: Проверка DNSSEC-записей

```bash
dig +dnssec www.lab.local @172.16.20.53
dig DNSKEY lab.local @172.16.20.53
dig +dnssec SOA lab.local @172.16.20.53
```

Ожидается:

* в ответе на `www` / SOA — секция с **RRSIG**;
* в ответе `DNSKEY` — открытые ключи зоны (KSK и ZSK).

Сохраните вывод (`dig +dnssec`) для домашнего задания.

### Шаг 6: Связь с третьей лабораторной

Подписи на сервере **ещё не защищают** Tiny Core в blue.net сами по себе: без валидирующего резолвера клиент может принять поддельный A от Ettercap (Lab 3).

DNSSEC останавливает spoofing только когда резолвер **проверяет** RRSIG по цепочке доверия (trust anchor). Для `lab.local` в GNS3 полного родителя в Интернете нет — свой валидатор и якорь доверия выходят за рамки этой работы.

Итог занятия: вы **включили DNSSEC на стороне авторитетного сервера** и научились это видеть через `dig`.

### Готово

Если `dig +dnssec` показывает **RRSIG**, а `dig DNSKEY lab.local` — ключи зоны, четвёртая лабораторная выполнена.

### Домашнее задание

Сдать к следующей встрече (или как завершение цикла):

1. Текст или скрин вывода `dig +dnssec www.lab.local @172.16.20.53`, где видна запись **RRSIG**.
2. Своими словами (5–8 предложений): чем отличаются **KSK** и **ZSK**; почему DNSSEC **не** является шифрованием DNS-трафика.
3. Мини-ответ (абзац): чего не хватает в нашей лаборатории, чтобы атака DNS Spoofing из третьей работы **гарантированно** отбивалась после подписания зоны.
