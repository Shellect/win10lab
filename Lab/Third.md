# Третья лабораторная работа

Эта работа продолжает [Первую](Первая%20лабораторная%20работа.md) и [Вторую](Вторая%20лабораторная%20работа.md) лабораторные: тот же MikroTik, сети **blue.net** / **red.net**, DNS на Alpine. Новая цель — увидеть угрозу **DNS Spoofing** и базовые способы защиты.

**Цель:** в изолированной лаборатории продемонстрировать подмену DNS-ответа (только для обучения) и обсудить защиту.

**Теория:** [Теоретический конспект к третьей лабораторной](../Notes/Теоретический%20конспект%20к%20третьей%20лабораторной.md). Подробно: [DNS Spoofing и DNSSEC](../Theory/DNS%20Spoofing%20и%20DNSSEC.md). Практика подписи зоны — [Четвёртая лабораторная работа](Четвёртая%20лабораторная%20работа.md).

Гипервизор — **VirtualBox**. Предполагается, что вторая лабораторная уже выполнена (DNS `www.lab.local` отвечает с `172.16.20.53`).

> Атакующие приёмы — только в своей учебной топологии GNS3, не в реальных сетях.

### Общий план

К топологии второй работы добавляется узел **Attacker** в клиентской сети (тот же L2, что и жертва — иначе ARP/DNS Spoofing через коммутатор не сработает).

| Сеть | Роль | Устройства | Задача |
| :--- | :--- | :--- | :--- |
| **blue.net** | Клиентская | Tiny Core PC1 (жертва), PC2; Attacker | Обычные DNS-запросы; имитация атаки |
| **red.net** | DMZ | Alpine + BIND9 | Настоящий авторитетный DNS (`lab.local`) |
| — | Маршрутизация / firewall | MikroTik | Связь blue ↔ red; правила из второй работы |

Почему Attacker в **blue.net**, а не «снаружи»:

* DNS Spoofing через ARP poisoning — атака **внутри одного широковещательного домена** (один коммутатор).
* MikroTik и firewall не «видят» подмену, если злоумышленник уже стоит между клиентом и шлюзом на L2.

### Шаг 1: Расширение топологии в GNS3

Исходная схема второй лабораторной:

```text
[Tiny Core PC1, PC2] → Switch1 → ether1 (MikroTik)   — blue.net
[Alpine DNS]         → Switch2 → ether2 (MikroTik)   — red.net
```

Добавьте на **Switch1** (blue.net) ещё один узел:

* **Attacker** — VirtualBox VM. Предпочтительно лёгкий **Alpine** с пакетами для атаки (`ettercap-gtk` или `ettercap` из репозитория community). Если места на диске хватает — **Kali Linux** (удобнее GUI Ettercap).

```text
[PC1, PC2, Attacker] → Switch1 → ether1 (MikroTik)   — blue.net
[Alpine DNS]         → Switch2 → ether2 (MikroTik)   — red.net
```

### Шаг 2: План адресации

Те же подсети, что в первой и второй работах:

| Сеть | Подсеть | Устройство | IP-адрес |
| :--- | :--- | :--- | :--- |
| **blue.net** | `172.16.10.0/24` | MikroTik `ether1` | `172.16.10.254` |
| | | PC1 (жертва) | `172.16.10.1` |
| | | PC2 | `172.16.10.2` |
| | | Attacker | `172.16.10.10` |
| **red.net** | `172.16.20.0/24` | MikroTik `ether2` | `172.16.20.254` |
| | | Alpine DNS | `172.16.20.53` |

На Attacker: IP `172.16.10.10/24`, шлюз `172.16.10.254`.

MikroTik и DNS на Alpine не перенастраивайте заново — используйте конфигурацию второй лабораторной. DNS: [Настройка DMZ в Alpine](../Theory/Настройка%20DMZ%20в%20Alpine.md).

### Шаг 3: Контрольная проверка «до атаки»

На PC1:

1. `ping 172.16.10.254`
2. `ping 172.16.20.53`
3. `nslookup www.lab.local 172.16.20.53` — должен быть **`172.16.20.53`**

Если это не так — сначала доведите до конца вторую лабораторную.

### Шаг 4: Подготовка Attacker (Ettercap)

На машине атакующего (пример для Kali; на Alpine команды аналогичны после установки ettercap).

1. Файл `/etc/ettercap/etter.conf`:
   * в `[privs]` задайте `ec_uid = 0` и `ec_gid = 0`;
   * в разделе для Linux раскомментируйте строки с `iptables` (для перенаправления).

2. Файл подмены `/etc/ettercap/etter.dns` — добавьте строку:

   ```text
   www.lab.local A 172.16.10.10
   ```

   Запрос имени `www.lab.local` будет получать IP **Attacker**, а не настоящего DNS в red.net.

3. (Опционально) Поднимите простой веб-сервер на Attacker, чтобы было видно подмену в браузере:
   * Kali: `sudo service apache2 start`
   * Alpine: `sudo apk add darkhttpd` и раздайте каталог с тестовой страницей.

### Шаг 5: Запуск DNS Spoofing (учебный сценарий)

1. Запустите Ettercap (GUI: `sudo ettercap -G`, либо CLI — по документации вашей ОС).
2. **Sniff** → **Unified sniffing** → интерфейс в blue.net (например, `eth0`).
3. **Hosts** → **Scan for hosts**, затем **Host List**.
4. Жертва `172.16.10.1` → **Add to Target 1**.  
   Шлюз `172.16.10.254` → **Add to Target 2**.
5. **MITM** → **ARP poisoning** → включите **Sniff remote connections**.
6. **Plugins** → **Manage the plugins** → активируйте **`dns_spoof`**.

На PC1 снова:

```bash
nslookup www.lab.local 172.16.20.53
```

или запрос без явного указания сервера (если в `resolv.conf` уже стоит `172.16.20.53`). При успешной атаке в ответе может оказаться **`172.16.10.10`** вместо `172.16.20.53`.

Суть: атакующий «обгоняет» или подменяет ответ, пока стоит человеком посередине (MITM) между клиентом и шлюзом.

### Шаг 6: Наблюдение и разбор

* Запустите захват на линке PC1↔Switch1 (Wireshark в GNS3): видны ARP и DNS.
* Сравните ответ DNS **до** и **после** включения плагина.
* Firewall на MikroTik (правила [Настройка Firewall](../Theory/Настройка%20Firewall.md) / второй работы) **не защищает** от этой атаки: она идёт внутри blue.net на L2, до маршрутизации в red.net.

### Шаг 7: Базовая защита (идеи для лаборатории)

Подробный разбор мер и DNSSEC — в [конспекте к третьей](../Notes/Теоретический%20конспект%20к%20третьей%20лабораторной.md) и [DNS Spoofing и DNSSEC](../Theory/DNS%20Spoofing%20и%20DNSSEC.md). Кратко для практики:

1. **Статическая запись на клиенте** (быстрый учебный контрпример): в `/etc/hosts` на PC1:
   ```text
   172.16.20.53   www.lab.local
   ```
   После этого имя не пойдёт через поддельный DNS-ответ. Проверьте `nslookup` / `ping www.lab.local` снова.

2. **DNSSEC** — подписи записей зоны (RRSIG) и цепочка доверия (DNSKEY → DS → … → trust anchor). Валидирующий резолвер отвергнет ответ Ettercap без корректной подписи. Практику подписи зоны на Alpine выполняйте в [Четвёртой лабораторной работе](Четвёртая%20лабораторная%20работа.md); на этом занятии достаточно объяснить принцип (см. теорию).

3. **Сегментация и контроль L2** — Port Security, Dynamic ARP Inspection на управляемых коммутаторах (в простой топологии GNS3 этого нет).

4. Не оставляйте учебный Attacker и Ettercap включёнными после занятия; верните проверку из шага 3.

### Готово

Если вы:

* видели корректный ответ DNS до атаки;
* получили подмену на IP Attacker при активном `dns_spoof`;
* смогли «отбить» подмену через `/etc/hosts` (или объяснили роль DNSSEC),

третья лабораторная выполнена: поверх маршрутизации MikroTik и DNS из предыдущих работ разобрана угроза DNS Spoofing и идея защиты.
