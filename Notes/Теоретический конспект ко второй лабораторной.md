## 1. Цель второй работы

Поверх маршрутизации первой лабораторной добавить **DNS** в сегменте **red.net** (Alpine + BIND) и проверить разрешение имён из **blue.net**. Между зонами — базовая политика **firewall** на MikroTik.

---

## 2. Сегменты blue.net и red.net

| Имя | Роль | Подсеть | Кто внутри |
| :--- | :--- | :--- | :--- |
| **blue.net** | Клиентская | `172.16.10.0/24` | Tiny Core PC1, PC2 |
| **red.net** | DMZ / серверная | `172.16.20.0/24` | Alpine + BIND9 |

Имена blue/red — учебные ярлыки на схеме. Рабочая DNS-зона — `lab.local`.

**DMZ** — зона для сервисов (здесь DNS): клиенты отдельно, сервер отдельно; между ними роутер/firewall.

---

## 3. OSI и TCP/IP (кратко)

| Уровень OSI | В лаборатории |
| :--- | :--- |
| L2 | Ethernet Switch в каждой зоне |
| L3 | MikroTik, IP `/24` |
| L4 | UDP/TCP порт 53 |
| L7 | DNS (BIND), `nslookup` / `dig` |

Стек TCP/IP: сетевой доступ → IP → TCP/UDP → приложения (DNS, HTTP, …).

Диагностика: нет ping до DNS → L3; ping есть, имя не резолвится → DNS (L7) или порт 53 / firewall (L4).

---

## 4. TCP и UDP

* **UDP** — без соединения, быстрее, без гарантии доставки. DNS обычно на **UDP/53**.
* **TCP** — надёжная доставка. DNS использует **TCP/53** для больших ответов и зон.

Поэтому в firewall разрешают оба протокола к `172.16.20.53`.

---

## 5. DNS

**DNS** переводит имя (`www.lab.local`) в IP (`172.16.20.53`) и обратно.

| Тип | Смысл | Пример |
| :--- | :--- | :--- |
| **A** | Имя → IPv4 | `www.lab.local` → `172.16.20.53` |
| **NS** | Сервер зоны | `ns1.lab.local` |
| **SOA** | Параметры зоны (Serial и др.) | файл зоны |
| **PTR** | IP → имя | обратная зона |

Прямая зона — имя→IP; обратная — IP→имя (`dig -x`).

В лаборатории BIND на Alpine — **авторитативный** master для `lab.local`.

Запрос: клиент blue → MikroTik → Alpine `172.16.20.53` → ответ A.

---

## 6. Шлюз

* Клиенты blue: шлюз `172.16.10.254`.
* Alpine red: шлюз `172.16.20.254`.

Без шлюза хост видит только свою подсеть.

---

## 7. Firewall

Правила на MikroTik (`/ip firewall filter`, цепочка **`forward`**):

* `accept` DNS (и при необходимости ICMP) blue → DNS;
* `established,related` — ответы на разрешённые сессии;
* `drop` инициации red → blue.

Порядок: сначала accept, потом drop. Подробно — [Настройка Firewall](../Theory/Настройка%20Firewall.md). Та же идея на Cisco/Juniper — [конспект вендоров](../Theory/Конспект%20MikroTik%20Cisco%20Juniper.md).

Firewall **не** защищает от DNS Spoofing внутри blue.net (это третья работа).

---

## 8. Связь с практикой

| Понятие | Где |
| :--- | :--- |
| Клиенты | blue.net, Tiny Core |
| DNS | red.net, Alpine `172.16.20.53` |
| Маршрутизация | MikroTik |
| Политика DMZ | filter forward |

**Итог:** вторая работа добавляет прикладной сервис DNS и базовое разграничение доступа между сегментами.
